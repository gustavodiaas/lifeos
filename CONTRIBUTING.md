# Contributing to LifeOS

Thank you for helping improve LifeOS. The project is being consolidated around a focused personal-planning workflow, so small, well-defined changes are preferred over new standalone modules.

## Before you start

- Search existing issues and pull requests.
- Open a feature request before starting a large change.
- Keep personal data, credentials, and production exports out of issues and commits.
- Report security and privacy problems according to [SECURITY.md](SECURITY.md).

## Local setup

1. Fork and clone the repository.
2. Install dependencies with `bun install`.
3. Copy `.env.example` to `.env.local`.
4. Configure a development Supabase project.
5. Run `bun run dev`.

Never use a production database for local development or automated tests.

## Development workflow

1. Create a branch from the latest `main`.
2. Keep the change focused and avoid unrelated formatting.
3. Preserve existing behavior unless the issue explicitly requires a product change.
4. Add or update documentation whenever behavior, setup, or data boundaries change.
5. Run the available validation commands before opening a pull request:

```bash
bun run lint
bun run build
```

Automated tests are not available yet. Adding a test foundation is a roadmap priority.

## Code conventions

- Use TypeScript and keep types explicit at data boundaries.
- Reuse components from `src/components/ui` before creating new primitives.
- Keep product modules under `src/modules` and routes under `src/routes`.
- Do not edit `src/routeTree.gen.ts` manually; it is generated by TanStack Router.
- Validate external input with Zod.
- Keep database field mapping at the data-access boundary instead of mixing `snake_case` and `camelCase` throughout UI components.
- Use Brazilian Portuguese for user-facing text until localization is introduced.

## Supabase and personal data

- Never commit project secrets, database passwords, secret keys, or `service_role` keys.
- Browser code may use only a public/publishable client key.
- Every table exposed through the Data API must have Row Level Security enabled and ownership policies reviewed.
- Include database migrations and policy changes in the repository when the Supabase foundation is added.
- Explain any new collection, storage, export, caching, or sharing of personal data in the pull request.

## Commit and pull request guidance

Use clear, imperative commit messages, for example:

```text
Add repository contribution guide
Fix task ownership filter
Improve mobile navigation spacing
```

Do not rewrite published history with force pushes, rebases, amended published commits, or squashed published commits. Pull requests should describe:

- the problem being solved;
- the chosen approach;
- how the result was verified;
- screenshots for visible interface changes;
- data or security impact, when applicable.
